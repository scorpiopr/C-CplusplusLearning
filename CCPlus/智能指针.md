# C++ 智能指针用法
智能指针实现自动管理内存，包含在 <memory> 头文件中，分为三种类型：
## 1. std::unique_ptr (独占指针) —— 最常用
它是最轻量、效率最高的一种。正如其名，同一时间只能有一个 unique_ptr 指向该对象。

### 特性：
	* 不可拷贝（不能把一个 unique_ptr 赋值给另一个）。
   * 可移动（通过 std::move 将所有权转交给别人）。
   * 对象生命周期结束时，自动释放内存。
### 用法：

```cpp
// 1. 创建（推荐使用 make_unique，C++14 起）
auto p1 = std::make_unique<int>(10);
// 2. 移动所有权（p1 变为空，p2 接管内存）
std::unique_ptr<int> p2 = std::move(p1);
// 3. 访问if (p2) 
cout << *p2;
// 4. 声明
unique_ptr<int> p1; // unique_ptr 默认初始化即为 nullptr，无需手动设置
```
### unique_ptr函数参数值传递（下沉模式）
要将 std::unique_ptr 作为参数传递给一个函数，并且不使用引用或指针（即采用值传递），必须使用 std::move() 将该指针的所有权显式地“转移”（Move）给函数。
因为 unique_ptr 具有“独占性”，它禁止了拷贝构造，所以直接传值会触发编译错误。

```cpp
#include <iostream>
#include <memory>
class Widget {
public:
    Widget(int id) : id_(id) { std::cout << "Widget " << id_ << " 被创建\n"; }
    ~Widget() { std::cout << "Widget " << id_ << " 被销毁\n"; }
    void doSomething() {
		std::cout << "Widget " << id_ << " 正在工作...\n";
	}
private:
	int id_;
};
// 💡 目标函数：接收一个同类型的 unique_ptr（值传递，非引用，非原始指针）
void processWidget(std::unique_ptr<Widget> w) {
    std::cout << "--- 进入 processWidget 函数内部 ---\n";
    if (w) {
        w->doSomething();
    }
    std::cout << "--- 离开 processWidget 函数内部 ---\n";
    // ⚠️ 关键点：w 是一个局部变量，生命周期在函数结束时终止，它所管理的 Widget 对象在此处被直接销毁！
}
int main() {
    // 1. 在 main 函数中创建 unique_ptr
    auto main_ptr = std::make_unique<Widget>(42);

    // ❌ 错误写法：processWidget(main_ptr); 
    // 编译报错！因为 unique_ptr 无法被复制（Copy Constructor is deleted）

    // ✅ 正确写法：使用 std::move 显式转移所有权
    processWidget(std::move(main_ptr));

    // 3. 检查转移后的状态
    std::cout << "--- 回到 main 函数 ---\n";
    if (main_ptr == nullptr) {
        std::cout << "main_ptr 此时已经变成 nullptr（空指针）了\n";
    }

    return 0;
}
```

运行结果（控制台输出）
```cpp
Widget 42 被创建
--- 进入 processWidget 函数内部 ---
Widget 42 正在工作...
--- 离开 processWidget 函数内部 ---
Widget 42 被销毁
--- 回到 main 函数 ---
main_ptr 此时已经变成 nullptr（空指针）了
```

#### 🔍 底层内存所有权是如何转移的？

   1. 调用前：main_ptr 独自拥有堆区 Widget(42) 的控制权和释放权。
   2. 执行 std::move(main_ptr) 时：C++ 强行将 main_ptr 转化为右值（Rvalue）。
   3. 函数参数绑定时：触发了 unique_ptr 的移动构造函数（Move Constructor）。此时，函数形参 w 接管了 Widget(42) 的堆内存地址，而 main_ptr 内部的指针被自动置为 nullptr。
   4. 函数结束时：因为 w 才是当前内存的唯一主人，随着 w 随着函数作用域消亡，Widget(42) 会立即在函数出口处被析构释放，而不需要等到 main 函数结束。

## 2. std::shared_ptr (共享指针)
它允许多个指针同时指向同一个对象。

### 特性：
  * 引用计数：内部维护一个计数器，记录有多少个 shared_ptr 指向该对象。
   * 自动释放：当最后一个 shared_ptr 销毁（计数归零）时，才真正释放内存。
### 用法：

```cpp
std::shared_ptr<Widget> sp1(new Obj(42)); // 构建方法一：缺点是有2次堆内存申请
auto sp1 = std::make_shared<string>("Hello"); // 构建方法二: 单次申请连续堆内存
{
    auto sp2 = sp1; // 计数变为 2
    cout << sp1.use_count(); // 查看引用计数
} // sp2 离开作用域，计数变为 1// sp1 离开作用域后，内存释放
```

* 构建方法一：传统的 new 有什么问题？
在底层会触发 2 次独立的堆内存申请（Heap Allocations）：

   * 第一次 new：在堆上申请空间，用于存放 Obj 对象本身。
   * 智能指针构造时：在堆上另开辟一块空间，用于存放 控制块（Control Block）（内部包含引用计数 use_count、弱引用计数 weak_count 等）。

* 构建方法二：std::make_shared

	* 内存完美合并（仅 1 次堆申请）：std::make_shared 在底层会一步到位地申请一块完全连续的、足够大的堆内存，将 Obj 对象和控制块打包放在一起。
	* 图解两者的内存对比：

```
【传统 new 方式（2次内存申请，碎片化）】
 堆区地址 A: [   Obj 对象   ]
 堆区地址 B: [ 控制块 (引用计数) ] <--- 离散分布，对 CPU 缓存不友好

【make_shared 方式（1次内存申请，连续空间）】
 堆区地址 C: [ 控制块 (引用计数) |   Obj 对象   ] <--- 绝对连续！
```

* std::make_shared 的 3 大压倒性优势

   1. 性能更高（CPU 缓存友好）：由于对象和控制块在物理内存上紧挨着，CPU 在读取它们时能实现极高的数据预取（Prefetching）命中率，大幅减少 Cache Miss。
   2. 降低内存碎片：将两次内存分配减为一次，减轻了操作系统的堆管理器（Heap Manager）的负担。
   3. 异常安全（Exception Safety）：
   在 C++17 之前，若写出类似 foo(std::shared_ptr<Widget>(new Widget()), g()); 的代码，如果 g() 抛出异常，可能导致 new 出来的对象来不及传给智能指针就造成内存泄漏。而 make_shared 是一个原子性的整体步骤，天然免疫这种泄漏。

* std::make_shared 不适用场景
	* 限制一：当类拥有私有/保护构造函数时（如单例模式）
std::make_shared 需要在它的函数内部去调用该类的构造函数。如果你的类把构造函数藏在了 private 内部，make_shared 将无权访问，导致编译失败。


	* 限制二：配合 weak_ptr 使用时的“内存延迟释放”隐患

		* 规则：只有当引用计数（shared_count）和 弱引用计数（weak_count）同时清零时，控制块才会被销毁。
		* 后果：在使用 make_shared 的情况下，因为对象和控制块死死绑定在同一块连续内存中，如果 shared_ptr 全都析构了（对象已经死亡），但还有一个 weak_ptr 指向它。此时，即使对象已经触发了析构函数，它所占用的那一块庞大的内存也无法归还给操作系统，必须等到 weak_ptr 也全部死掉，整块内存才能整体释放。
### 线程安全
std::shared_ptr **不是绝对线程安全的**。 它的线程安全级别和内置的普通指针（如 int*）完全相同。
具体表现可以拆解为以下三个核心部分：
1. 引用计数：完全线程安全 🔒
* 机制：shared_ptr 内部包含一个指向管理数据的指针和一个指向控制块（存储引用计数、销毁器等）的指针。
* 表现：控制块中的引用计数增减操作是原子的。
* 结果：多个线程同时拷贝（按值传递）或析构不同的 shared_ptr 对象，且这些对象指向同一个堆内存时，引用计数绝对安全，不会发生内存泄漏或重复释放。

2. 指向的对象：不线程安全 ❌
* 表现：shared_ptr 只负责管理对象的生命周期，不提供对象内部数据的同步机制。
* 结果：如果多个线程通过各自的 shared_ptr 同时修改同一个底层对象的数据（例如同时往一个 std::vector 里 push_back），会导致数据竞争。这需要开发者自己在对象层面进行锁保护。 

3. 指针对象本身：不线程安全 ❌
* 表现：由于 shared_ptr 对象本身由“数据指针”和“控制块指针”两个部分组成，对智能指针本身的赋值或重置（如 ptr = c）不是原子操作。  
* 结果：如果多个线程同时读写同一个 shared_ptr 对象，例如：
	* 线程 A 正在执行 ptr = ptr_new;（涉及旧内存释放、修改两个指针指向等多个步骤）。
	* 线程 B 正在执行 auto p = ptr;（读取数据指针和控制块指针并复制）。
	   由于这两个步骤之间没有原子性保护，会导致脏读、野指针甚至程序崩溃。

## 总结对照表

| 操作场景 | 是否线程安全 | 解决方案 / 备注 |
|---|---|---|
| 不同线程 读写 不同 的 shared_ptr 实例（指向同一对象） | 是 | 引用计数的增减由底层原子操作保证。 |
| 不同线程 读写 相同 的 shared_ptr 实例本身 | 否 ❌ | 必须加锁（如 std::mutex），或改用 std::atomic<std::shared_ptr<T>>（C++20起支持）。 |
| 不同线程 读写 智能指针 指向的底层数据 | 否 ❌ | 需要在业务代码中加锁，或者对象本身就是线程安全的容器。 |


## 3. std::weak_ptr (弱指针)
它是 shared_ptr 的“助手”，不参与引用计数。

* 解决**循环引用**：如果两个类互相持有 shared_ptr，引用计数永远不会降到 0，导致内存泄漏。将其中一方改为 weak_ptr 即可解决。

    ```cpp
    #include <iostream>
    #include <memory>
    class Boy; // 前置声明
    class Girl {
    public:
        std::shared_ptr<Boy> boyfriend; // 强引用指向 Boy
        ~Girl() { std::cout << "[Girl] 被安全析构了！\n"; }
    };
    class Boy {
    public:
        std::shared_ptr<Girl> girlfriend; // 强引用指向 Girl
        ~Boy() { std::cout << "[Boy] 被安全析构了！\n"; }
    };
    void memory_leak_leak_leak() {
        // 1. 在堆区创建两个对象，此时它们的强引用计数各自为 1
        auto tom = std::make_shared<Boy>();
        auto lucy = std::make_shared<Girl>();
    
        // 2. 🔑 致命互锁：让彼此内部的指针互相指向对方
        tom->girlfriend = lucy; // lucy 的强引用计数变为 2
        lucy->boyfriend = tom;  // tom 的强引用计数变为 2
        
        // 3. 函数结束，局部变量 tom 和 lucy 销毁（它们各自让对方的引用计数减 1）
        // 此时按理说应该触发析构，但奇迹（灾难）发生了……
    }
    int main() {
        memory_leak_leak_leak();
        std::cout << "函数结束了，堆内存真的释放了吗？\n";
        return 0;
    }
    ```

   1. 当函数结束时，栈上的局部变量自发析构，它们通过底层控制块将 Boy 和 Girl 的强引用计数各自从 2 扣减为 1。
   2. 智能指针触发释放的铁律是：“只有当强引用计数等于 0 时，才允许销毁对象并调用析构函数。”
   3. 此时，要想销毁 Boy 对象，就必须先销毁其内部的 girlfriend 指针；而要销毁 girlfriend 指针，就必须先释放 Girl 对象；而要释放 Girl 对象，又必须先销毁其内部的 boyfriend 指针……
   4. 逻辑陷入了经典的因果鸡蛋死循环。这就好比两个人互相抓着对方的衣领悬空挂在悬崖边，谁也不松手，结果就是一起在内存里永世僵死。

    改为使用std::weak_ptr 仅仅是一种对对象的“旁观监督者”，它只会指向对象，但绝对不会增加对象的【强引用计数】。它只能从一个 std::shared_ptr 或另一个 std::weak_ptr 中诞生。

  ```cpp
  class Boy;
  class Girl {public:
      std::shared_ptr<Boy> boyfriend; // 依然是强引用
      ~Girl() { std::cout << "[Girl] 被安全析构了！\n"; }
  };
  class Boy {public:
      // 🔑 完美破局：改成弱引用！女朋友只是“旁观”男朋友，不强制捆绑他的生命
      std::weak_ptr<Girl> girlfriend; 
      ~Boy() { std::cout << "[Boy] 被安全析构了！\n"; }
  };
  void perfect_free() {
      auto tom = std::make_shared<Boy>();   // tom 强计数 = 1
      auto lucy = std::make_shared<Girl>(); // lucy 强计数 = 1
  
      tom->girlfriend = lucy; // 🔑 注意：因为是 weak_ptr，lucy 的强计数依然是 1！
      lucy->boyfriend = tom;  // tom 的强计数变为 2
  
      // 函数结束：
      // 1. 局部变量 lucy 销毁，让 Girl 的强计数归 0！Girl 当场引爆析构！
      // 2. Girl 析构的同时，会顺手将它持有的 boyfriend 指针销毁，让 Boy 的强计数从 2 跌落到 1。
      // 3. 局部变量 tom 销毁，让 Boy 的强计数从 1 归 0！Boy 当场引爆析构！
  }
  ```
* 安全观测：它能知道对象是否还存在，但不能直接操作。要使用时需通过 lock() 临时转回 shared_ptr。
  
  ```cpp
  std::weak_ptr<string> wp = sp1;
  if (auto temp = wp.lock()) { // 如果对象还在，返回一个 shared_ptr
      cout << *temp;
  }
  ```

## 💡 核心规则与面试考点

1. 优先使用 unique_ptr：如果不需要多个指针共享同一个对象，首选 unique_ptr。因为它几乎没有性能开销。
2. 避免手动 new / delete：除非是在写底层数据结构（如刚才的 TrieNode 练习），否则在业务代码中应全面使用智能指针。
3. 传参建议：
 * 如果只是使用对象，不涉及所有权，函数参数直接传 原始指针 (ptr.get()) 或 引用 即可。
  * 不要轻易在函数参数里传 shared_ptr 的值，因为每次拷贝都会触发原子操作修改引用计数，影响性能。

## 总结比较

| 类型 | 拷贝性 | 所有权 | 性能 | 场景 |
|---|---|---|---|---|
| unique_ptr | ❌ 禁止 | 唯一拥有 | 极快（同原始指针） | 树节点、单例、局部资源管理 |
| shared_ptr | ✅ 允许 | 共同拥有 | 稍慢（有计数开销） | 缓存、多线程资源共享 |
| weak_ptr | ✅ 允许 | 不拥有 | 快 | 解决循环引用、缓存观察者 |
